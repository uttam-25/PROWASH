# PROWASH Phase 1 — Backend scaffold and mobile auth shell

Phase 1 delivers the Node.js/Express/MongoDB auth API (FEAT-001) and the React Native/Expo mobile scaffold with a complete auth screen set (FEAT-002). Both features are marked `completed`, the bundle compiled to 1116 modules with exit 0, and the core security invariants (role forced to `customer` on registration, JWT in SecureStore, auth-state-gated navigation) are correctly implemented. One hardcoded `'#000'` shadow color survives in `ConfirmDialog.js` after the fix commit, and the `protect` middleware passes `JsonWebTokenError` and `TokenExpiredError` to the generic error handler, which returns 500 instead of 401 for expired or malformed tokens.

Watch for: (confirmed) `ConfirmDialog.js` line 90 retains `shadowColor: '#000'` — the fix commit that cleaned up `CustomerNavigator.js` and `AdminHomeScreen.js` missed this file. (confirmed) In `middleware/auth.js`, `jwt.verify` exceptions are not typed before being forwarded: expired and tampered tokens produce 500 responses in the current error handler, breaking client-side re-authentication.

**Verdict**: CHANGES_REQUESTED

## High-level view

All 15 acceptance criteria pass except two. The server has `"type":"module"`, the User model has `role` defaulting to `'customer'` with `password: { select: false }`, `register` rejects `role === 'admin'` with 403 and hard-forces `role: 'customer'` on create, `protect` returns 401 for a missing token, `requireAdmin` returns 403, `App.js` renders the required provider tree, `RootNavigator` gates correctly by auth state, token storage is `expo-secure-store`, no TypeScript files exist outside `node_modules`, the Expo bundle succeeded, `GET /api/health` exists, and `README.md` is present.

The two failures: `ConfirmDialog.js` has a hardcoded `'#000'` that the fix commit skipped, and `protect`'s catch block forwards JWT library exceptions without converting them to `AppError(401)`, so expired/malformed tokens produce 500 responses in development (with stack trace) and 500 in production — clients cannot distinguish this from a server fault and will not re-authenticate.

### JWT error handling in `protect` middleware

```js
// current (auth.js)
} catch (err) {
  next(err);  // JsonWebTokenError or TokenExpiredError passed as-is → 500
}
```

`jsonwebtoken` throws typed errors that are not `AppError` instances. The error handler reads `err.statusCode` (undefined on JWT errors) and defaults to 500. In development the response includes a stack trace. A client that receives 500 on an expired token cannot distinguish it from a server fault, so the `setLogoutCallback` wired in `AuthContext` (which fires on 401) never triggers — the user stays in a broken state until they manually log out. The fix:

```js
} catch (err) {
  if (err.name === 'JsonWebTokenError' || err.name === 'TokenExpiredError') {
    return next(new AppError('Invalid or expired token', 401));
  }
  next(err);
}
```
