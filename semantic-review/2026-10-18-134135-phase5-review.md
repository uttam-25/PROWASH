# Phase 5: Payments and Notifications

Phase 5 wires in two major capabilities: a full Razorpay payment flow (order creation, verification, webhook processing) and a richer notification system (semantic helpers, PATCH routes, unread badge). The backend replaces stub payment functions and generic `Notification.create` calls with typed helpers and proper field names (`bookingId`/`customerId`). The mobile side delivers a working post-booking `PaymentScreen`, an active Pay Online chip in `BookWashScreen`, and an unread badge on the home screen bell. All 14 plan items were implemented and the Expo bundle exits 0.

Watch for: (1) **confirmed** — webhook signature check returns 400 (not 200) when no secret env vars are configured and a request arrives; this is a minor deviation from the "always 200" contract but is deliberate rejection of invalid requests. (2) **confirmed** — `recordCODCollection` drops the notification silently when `booking` is null, which was pre-existing but is now more visible because the generic `Notification.create` fallback is gone.

**Verdict**: APPROVED

## High-level view

All backend field name references (`booking`→`bookingId`, `customer`→`customerId`) are consistently updated across `paymentController`, `bookingController`, and `getPayment`/`getAllPayments`. No legacy field names survive in the new code.

Notification routes are PATCH throughout — both the route file and the mobile `notificationService.js` use `.patch()`. The `GET /api/notifications` response shape changed from a bare array to `{ data: { notifications, unreadCount } }`, and all three callers (NotificationsScreen, CustomerHomeScreen badge, the new `getNotifications(true)` call) parse the new shape correctly.

The payment controller's `RAZORPAY_NOT_CONFIGURED` 503 path is confirmed in both the backend (returns 503 with `code: 'RAZORPAY_NOT_CONFIGURED'`) and the mobile client (checks `status === 503 || code === 'RAZORPAY_NOT_CONFIGURED'` before entering `cod_fallback` state). `PaymentScreen` never imports `react-native-razorpay`; the string only appears as display text.

The webhook handler catches all thrown errors and returns 200 from the catch block, satisfying the "always 200 on processing errors" contract. The one case that returns 400 is a deliberate signature rejection — not a processing error.

The `recordCODCollection` path in `adminController` no longer notifies when `booking` is null (the `if (booking)` guard drops it silently). This is narrower than before, where `Notification.create` used `customerId` from `payment` directly and would notify even without a booking object.

<details>
<summary>Issues (2)</summary>

1. **Webhook silent-drop on missing secret** — When both `RAZORPAY_WEBHOOK_SECRET` and `RAZORPAY_KEY_SECRET` are unset, the HMAC is computed with an empty-string secret. Any real Razorpay request will fail signature validation and get 400. In dev with no secret configured, all webhook calls will be rejected. Add a guard that returns 200 immediately (or logs a warning) when the secret is not configured, so webhook testing doesn't silently break.

2. **COD collection notification lost when booking is null** — In `recordCODCollection`, the new code only calls `notifyPaymentConfirmed` when `booking` is truthy. If `booking` is null (payment exists but booking was deleted or lookup failed), the customer gets no payment confirmation notification. The old code used `payment.customerId` directly. Consider falling back to `payment.customerId` for the notification even when the full booking object is unavailable.

</details>

<summary>Details</summary>

### RAZORPAY_NOT_CONFIGURED path and mobile fallback

`createRazorpayOrder` checks `process.env.RAZORPAY_KEY_ID && process.env.RAZORPAY_KEY_SECRET` before doing anything Razorpay-related and returns 503 with `code: 'RAZORPAY_NOT_CONFIGURED'`. `PaymentScreen` catches this on both `status === 503` and `code === 'RAZORPAY_NOT_CONFIGURED'`, so the fallback triggers on either signal. The `cod_fallback` state shows a confirmation screen with the booking reference and a "View My Bookings" button — the user is never left on a dead screen.

### Webhook always-200 contract

The outer `try/catch` in `handleWebhook` does return 200 from the catch block with `{ received: true }` for any processing error. The one non-200 path is the signature mismatch check (returns 400), which is intentional — Razorpay interprets a non-200 response as "not received" and will retry. The risk is that when no secret is configured (`secret || ''`), every legitimate Razorpay call will be rejected with 400. This won't crash the server, but it means webhook events will never be processed in environments without the secret set. A startup-time warning or a short-circuit 200 for the unconfigured case would reduce confusion.

### COD notification regression

Old code: `Notification.create({ user: customerId })` where `customerId = booking ? booking.customerId : payment.customerId`. New code: `if (booking) { notifyPaymentConfirmed(booking, null) }`. When `booking` is null, no notification fires. The `payment.customerId` path is gone. This is confirmed by reading the adminController diff — the fallback to `payment.customerId` was not carried over to the new helper call.

### BookWashScreen navigation and field names

`handleConfirmBooking` extracts `const booking = result.data` and passes `booking._id` and `booking.bookingReference` to the Payment screen. The booking model exposes both fields. The `else` branch still uses `result.data` directly (redundant but not wrong). Pay Online chip is a live `TouchableOpacity` with `accessibilityRole="radio"` — accessible and consistent with the COD chip styling.

### Notification route PATCH migration

Both `router.put` calls in `notificationRoutes.js` are now `router.patch`. The mobile `notificationService.js` calls `api.patch` for both `markRead` and `markAllRead`. `getNotifications(true)` passes `{ params: { read: 'false' } }`. The backend filter check is `req.query.read === 'false'` (string comparison) which matches correctly.
